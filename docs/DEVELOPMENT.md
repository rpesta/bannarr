# Developing Bannarr

Working notes for this repo, kept out of the README so it stays about installing and using
Bannarr. Everything is in one file, `bannarr.sh`, and there is no build step. Every function has
a doc comment, and the sections below explain how the pieces fit together.

```bash
bash -n bannarr.sh                       # syntax-check the editor
BANNARR_ETC_DIR=/tmp/bn/etc bash bannarr.sh --apply   # run against a fake /etc (see below)
sh -n /tmp/bn/etc/profile.d/00_bannarr.sh             # syntax-check a generated banner
shellcheck -s sh /tmp/bn/etc/profile.d/00_bannarr.sh  # if shellcheck is installed
```

## How it works

```
                 ┌──────────── bannarr.sh (bash TUI) ─────────────┐
 /etc/bannarr/   │                                                │
  bannarr.conf ──┼─► load_state ─► BN_* vars + ART_LINES          │
  banner.txt   ──┘                     │                          │
                                       ▼                          │
                              build_profile  ── prints ──►  settings + renderer + art
                                       │                          │
                    draw (every menu loop): sh <tmpfile>  ◄── live preview
                    save_apply:           sh -n, then write ──► /etc/profile.d/00_bannarr.sh
                                          rename 00_lxc-details.sh ──► *.bannarr-disabled
                 └────────────────────────────────────────────────┘
```

1. **Settings are shell variables.** All settings are `BN_*` variables (see
   [Settings reference](#settings-reference)). The menus edit them in memory, and `write_conf`
   prints them as safely quoted `sh` assignments.
2. **One renderer, two uses.** `emit_renderer` prints a block of POSIX `sh` functions
   (`_bn_*`) that collect values and draw the banner. That block is
   - copied word for word into the generated profile script, and
   - `eval`'d into the bash editor, so the menus reuse the same labels, icons and colors.
3. **The generated profile script is self-contained.** `build_profile` writes:

   ```sh
   # Generated by Bannarr ...
   if [ -t 1 ] && [ -z "${BANNARR_SHOWN:-}" ]; then (
     BN_TITLE='Plex LXC Container' ...  # settings (write_conf)
     _bn_c() { ... }                    # renderer (emit_renderer)
     ...
     _bn_art() { cat <<'__BANNARR_ART__'
     ...art lines...
     __BANNARR_ART__
     }
     _bn_show
   ); fi
   BANNARR_SHOWN=1; export BANNARR_SHOWN
   ```

   - `[ -t 1 ]` keeps non-interactive sessions (`scp`, `rsync`, `ssh host cmd`) silent.
   - The `( ... )` subshell keeps Bannarr's variables and functions out of the login shell.
     The one exception is `BANNARR_SHOWN`, which is exported so the banner doesn't repeat in
     nested shells, tmux or screen. RHEL-likes source `profile.d` from `/etc/bashrc` for every
     interactive shell, so without it the banner would show each time.
   - Login never reads `/etc/bannarr/`, so the banner keeps working if that folder is deleted.
4. **The live preview runs the real thing.** `draw` runs `build_profile preview` into a temp
   file, executes it with `sh` and captures the output.
   - **Preview mode** drops only the `[ -t 1 ]` terminal check. The captured output isn't a
     terminal, so the real check would print nothing; this caused an empty preview once.
     Everything else is the script that gets installed.
   - **Cached:** the output is kept under a signature of all `BN_*` variables and the art,
     and only rebuilt when that changes. So menus can redraw on every keypress without
     re-sampling the CPU each time; values refresh when a setting changes.
   - **Menus:** they are drawn under the preview by `menu_pick` (single choice) and
     `menu_check` (checklist), plus the custom checklists in `items_menu` and `text_menu`.
     `read_key` turns arrow keys and other escape sequences into names like `up` and `enter`.
     Neither needs whiptail, which would hide the preview and isn't installed by default on
     Alpine, Fedora or Arch.
   - **`MENU_ON_MOVE`** lets a menu change a setting as the highlight moves (gallery, fonts,
     colors) and put it back on Esc.
5. **Saving is guarded.**
   - **Asking first:** in the editor, `save_menu` runs only when there are unsaved changes.
     It asks Save or Cancel, then `ask_backup` offers to copy the currently saved design into
     the **single** backup slot, `/etc/bannarr/backup/`. It does that only if a saved design
     exists, and replaces any previous backup. It prints the backup's location and the
     `--restore` command.
   - **Syntax check:** `save_apply` writes the new script next to the live one and runs
     `sh -n` on it; nothing changes unless that passes.
   - **Swapping in:** only then does it disable the community-scripts banner, swap in the new
     file, and print the `--revert` command.
   - **No automatic backups:** there are no named backups, no backup library, and
     `save_apply` itself never makes a backup. The command-line options (`--apply`,
     `--restore`) never prompt.

## Files on the target system

| Path | Purpose |
| ---- | ------- |
| `/etc/profile.d/00_bannarr.sh` | The generated banner, run at login |
| `/etc/profile.d/00_lxc-details.sh.bannarr-disabled` | The community-scripts banner, switched off but unchanged |
| `/etc/bannarr/bannarr.conf` | Saved settings (`BN_*` assignments, mode 600) |
| `/etc/bannarr/banner.txt` | Saved ASCII art, one line per line |
| `/etc/bannarr/backup/` | The one backup (`bannarr.conf` + `banner.txt`): the design from before the last save, made only when the user says yes |
| `/etc/bannarr/share-command.txt` | The last share command shown by **c → 1**, for easy copying |
| `/etc/motd.bannarr-disabled` | `/etc/motd` while login messages are quiet |
| `/etc/bannarr/quiet/` | Record of quieted login messages: `enabled` marker, `update-motd.d.list` (original modes), `motd.d/` (moved entries) |

Nothing else is touched: no `sshd_config`, PAM, user dotfiles or packages. Bannarr never
installs anything (see [Zero dependencies](#zero-dependencies)).

## Coexisting with community-scripts

Nothing runs `00_lxc-details.sh` by name. At login, `/etc/profile` runs every
`/etc/profile.d/*.sh` (Debian, Ubuntu, Alpine, Fedora/RHEL, Arch and openSUSE all do this).

| | Community-scripts box | Any other box |
| --- | --- | --- |
| **Save** | Writes `00_bannarr.sh` and `park`s `00_lxc-details.sh` as `00_lxc-details.sh.bannarr-disabled`, which no longer matches `*.sh` | Writes `00_bannarr.sh` |
| **Revert** | Deletes `00_bannarr.sh` and `unpark`s the original | Deletes `00_bannarr.sh` |
| **Default design** (`set_defaults`) | `BN_TITLE` = the original banner's title, `BN_CREDITS` = its "Provided by" line | No title, no credits |
| **First run** (`first_run_cs`) | "community-scripts container detected": a `menu_check` list of Banner Title and Credits, both ticked. Unticking clears `BN_TITLE` or sets `BN_CREDITS_ON=no`, live through `MENU_ON_TOGGLE`. Then a Hide / Keep `menu_pick` for the `/etc/motd` copy | Nothing asked |

`is_cs_box` decides which column applies: the original file is present, active or parked.
`cs_banner_lines` reads the title ("… LXC Container") and credit ("Provided by: …") lines from
that file. It drops the `echo -e "…"` wrapper, color codes (real escape bytes or literal
`\033[…m` and `\e[…m`) and extra spaces, so the text matches what the original banner showed,
emoji included. Nothing is hard-coded, so a change to the community-scripts wording carries
through. If the lines can't be found, the design simply starts without them.

Community-scripts doesn't require the credit to be shown: its MIT license covers copies of
its scripts, not the output they write onto a user's machine. Keeping the credit by default
is a courtesy, and it makes a future submission to community-scripts easier. If
an installer recreates `00_lxc-details.sh`, the next `--apply` parks the newer copy as
`*.bannarr-disabled.<timestamp>`, so `--revert` still restores the original.

## Quieting other login messages

| Source | Shown by | `quiet_motd` | `unquiet_motd` |
| ------ | -------- | ------------ | -------------- |
| `/etc/update-motd.d/*` | `pam_motd` via `run-parts` | `chmod a-x` on each executable script, recording `stat -c %a` first. Renaming isn't safe: `run-parts --lsbsysinit` still runs some dotted names | Restores each recorded mode |
| `/etc/motd` | `pam_motd` or sshd `PrintMotd` | `park` | `unpark` |
| `/etc/motd.d/*` | `pam_motd` | Moves entries into `QUIET_DIR/motd.d`, because `pam_motd` shows every file there whatever its name | Moves them back unless the name is taken |

`save_apply` re-runs `quiet_motd auto` while quiet mode is on, to catch scripts a package
upgrade re-enabled. `uninstall` never deletes `QUIET_DIR` while it still holds originals that
couldn't be moved back. `/run/motd.d` (runtime) and `/usr/lib/motd.d` (package-owned) are out
of scope, as is the `Last login` line (sshd `PrintLastLog`).

## Where values come from

| Key | Label | Source (first that works) | Bar |
| --- | ----- | ------------------------- | :-: |
| `hostname` | Hostname | `/proc/sys/kernel/hostname` → `hostname` | |
| `fqdn` | FQDN | `hostname -f` | |
| `ip` | IPv4 | `ip -4 addr` (global) → `hostname -I` → `ifconfig` | |
| `ipv6` | IPv6 | `ip -6 addr` (global) | |
| `os` | OS | `/etc/os-release` `PRETTY_NAME` → `NAME` → `uname -s` | |
| `kernel` / `arch` | Kernel / Arch | `uname -r` / `uname -m` | |
| `uptime` | Uptime | `/proc/uptime` | |
| `load` | Load | `/proc/loadavg` | |
| `cpu` | CPU | `/proc/stat` sampled over 0.2 s | ✓ |
| `cpu_model` / `cores` | CPU Model / Cores | `/proc/cpuinfo` | |
| `memory` | Memory | `/proc/meminfo` `MemAvailable` (older kernels: Free+Buffers+Cached) | ✓ |
| `swap` | Swap | `/proc/meminfo` | ✓ |
| `disk` | Disk (/) | `df -Pk /` (the `NN%` column is located, so filesystem names with spaces parse) | ✓ |
| `mounts` | *(mount path)* | `/proc/mounts` + `df -Pk`, one row per mount | ✓ |
| `procs` | Processes | `/proc/[0-9]*` | |
| `users` | Users | `who` | |
| `date` | Date | `date` | |

`mounts` skips pseudo filesystems, `/proc` `/sys` `/dev` `/run` `/boot/efi`, and LXC's
single-file bind mounts (only directories are kept). In auto mode it skips `/` while `disk` is
enabled. In LXC, `/proc/stat` is usually the host's; memory and disk are per-container through
LXCFS.

## Settings reference

All settings live in `bannarr.conf` and are embedded in the profile script.

| Variable | Default | Meaning |
| --- | --- | --- |
| `BN_TITLE` | the community-scripts title, else empty | Banner title, printed under the art. Empty = none |
| `BN_C_TITLE` | `bold` | Banner title color |
| `BN_CREDITS` | the community-scripts "Provided by" line, else empty | Credits line, printed under the title in `BN_C_TEXT` |
| `BN_CREDITS_ON` | `yes` | Show the credits (`no` hides them but keeps the text) |
| `BN_ITEMS` | `os hostname ip uptime cpu memory disk` | Space-separated display order: item keys and `textN` static lines |
| `BN_TEXT_<n>` | *(none)* | Static text line `n` |
| `BN_TC_<n>` | *(empty)* | Color override for text line `n` |
| `BN_LAYOUT` | `list` | `list`, `columns` or `inline` |
| `BN_INDENT` | `2` | Spaces before every line |
| `BN_LABEL_W` | `10` | Label column width (`list`/`columns`) |
| `BN_VALUE_W` | `26` | No longer used: `_bn_colw` sizes the `columns` layout's left column to the widest cell (bar + value + label overflow). Still accepted in saved designs and share codes |
| `BN_SEP` | `: ` | Text between label and value |
| `BN_BAR` | `yes` | Show usage bars (all items; `BN_B_<key>` overrides one item) |
| `BN_B_<key>` | *(empty = follow `BN_BAR`)* | `yes`/`no`: usage bar for one item (`cpu`, `memory`, `swap`, `disk`, `mounts`) |
| `BN_BAR_W` | `10` | Bar width in cells |
| `BN_BAR_FULL` / `BN_BAR_EMPTY` | `█` / `·` | Bar characters. The fill takes the threshold or value color and the empty track the separator color. `░` was dropped as the default because some fonts lack it and the substitute glyph overflows its line |
| `BN_THRESH` | `yes` | Color bar fills green / yellow (60%+) / red (85%+) by usage. Without a bar, the value keeps `BN_C_VALUE` and turns yellow or red only at 60%+, so switching a bar off never changes normal text colors |
| `BN_ICONS` | `unicode` | Icon set: `off`, `unicode` (code page 437 symbols only), `emoji` |
| `BN_MOUNTS` | *(empty = auto)* | `\|`-separated mount points for the `mounts` item |
| `BN_ART_COLOR` | ocean gradient | One color, or a space-separated list spread over the art's lines: line `i` of `n` gets color `1 + i*(m-1)/(n-1)` of `m`, so it always runs first to last. `GRADIENTS` holds 18 named lists |
| `BN_ART_SRC` | `hostname` | `hostname` or `text` (built-in font, redrawn on every load) or `custom` (from `banner.txt`) |
| `BN_ART_TEXT` | *(empty)* | The text drawn when `BN_ART_SRC=text` |
| `BN_ART_SIZE` | `auto` | `1`–`3` scales block-letter art. `auto` = 2x if that fits 78 columns × 6 rows, else 1x, so the 4-row built-in font stays at 1x and only small art is doubled. Art with other characters (figlet, Tux) is never scaled |
| `BN_C_LABEL` / `BN_C_VALUE` | `yellow` / `bgreen` | Label and value colors |
| `BN_C_SEP` / `BN_C_TEXT` / `BN_C_ICON` | `gray` / `gray` / `cyan` | Separator, static text and icon colors |
| `BN_L_<key>` | *(empty)* | Label override for an item |
| `BN_VC_<key>` | *(empty)* | Value color override for an item |
| `BN_I_<key>` | *(empty)* | Icon override for an item |

**Color specs** (`_bn_c`): `none`, `black`, `red`, `green`, `yellow`, `blue`, `magenta`,
`cyan`, `white`, `gray`, a `b` prefix for bold (`bred`, `bcyan`...), or a 256-color number
`0`–`255`.

## Zero dependencies

Bannarr must work on a stock box with nothing added, like the community-scripts banner it
replaces:
- **Never install packages.** If figlet happens to be installed, the generator also lists its
  fonts, but Bannarr never offers to install it.
- **Never require a special font.** Nerd Font icons were removed for this reason.
  - **Icons:** the `unicode` set uses only symbols from the original PC character set (code
    page 437: `⌂ ↔ ♦ ▲ ► ↑ ≈ ■ ∙ ▬ ↕ ◘ ≡ ☺ ○`), which practically every terminal font has.
    Earlier picks such as `▣ ⇄ ◫` showed as `?` boxes on a real container.
  - **Bars:** use characters that stock terminal fonts have.
  - **ASCII art:** the built-in font is drawn with `█ ▀ ▄` only.
- **Assume no UTF-8 locale.** Minimal containers often run in the `C` locale, where bash
  counts and slices strings in bytes. Never take one character of a string that may hold
  multi-byte characters with `${s:i:1}`. Replace whole sequences with `${s//█/#}`, as
  `art_to_px` does, or split on an ASCII separator, as the bar presets do with `"█|·"`.

## Rules for the renderer

Everything inside `emit_renderer`'s heredoc runs under dash and busybox ash at login, so it
must stay **POSIX sh**: no arrays, `[[ ]]`, `local`, `$'...'` or `${var^^}`. Store unusual
characters as `printf` octal escapes if editors or copy/paste might drop them.

## Testing without touching `/etc`

`BANNARR_ETC_DIR` stands in for `/etc`, so every file Bannarr touches (`profile.d`, `motd`,
`motd.d`, `update-motd.d`, and `bannarr/` for settings) lands in a test folder. It also skips
the root check. `BANNARR_DIR` moves just the settings folder. To simulate a community-scripts
box with an Ubuntu-style MOTD:

```bash
export BANNARR_ETC_DIR=/tmp/bn/etc E=/tmp/bn/etc
mkdir -p "$E/profile.d" "$E/update-motd.d" && echo 'echo STOCK' > "$E/profile.d/00_lxc-details.sh"
echo 'Welcome!' > "$E/motd" && printf '#!/bin/sh\necho hi\n' > "$E/update-motd.d/10-help" && chmod 755 "$E/update-motd.d/10-help"
bash bannarr.sh --apply && bash bannarr.sh --quiet-motd
ls "$E" "$E/profile.d"; stat -c '%a %n' "$E"/update-motd.d/*   # parked + 644
BANNARR_SHOWN= sh "$E/profile.d/00_bannarr.sh"                  # needs a terminal
bash bannarr.sh --revert && ls "$E" "$E/profile.d"               # everything back, 755 again
```

Check that the editor's preview actually has content. It once came out empty because of the
terminal check described in [How it works](#how-it-works):

```bash
sed '$d' bannarr.sh > /tmp/bn_lib.sh   # the script without its final "main" call
BANNARR_ETC_DIR=/tmp/bn/etc bash -c '. /tmp/bn_lib.sh; load_state; draw x >/dev/null; [ -n "$PREVIEW_OUT" ] && echo preview OK'
```

Git Bash on Windows can run most of this, but it reports any file that starts with `#!` as
executable whatever its mode, so test the `update-motd.d` handling on real Linux.

## Share codes

A share code copies a design to another server: `bannarr1:` plus the base64 of the
gzip-compressed `design_payload`. It's `bannarr0:` and plain base64 when gzip is missing;
`base64` and `gzip` ship with coreutils and busybox. The payload is plain text:

```
# Bannarr design
title=auto          # the title is this box's community-scripts title: use the target's own
quiet=yes           # other login messages are quiet here: quiet them there too
BN_LAYOUT='columns' # every BN_* setting, in write_conf's quoting...
...                 # ...except BN_CREDITS, and BN_TITLE when title=auto
__ART__
<art lines>         # only for custom art; hostname and text art are redrawn on the target
```

**Importing is safe by construction.** `import_design` never sources, evals or runs any part
of a code:
1. **Format check.** Every line must be a note it knows, `__ART__`, or
   `BN_NAME='value'` in write_conf's quoting, where `valid_setting` accepts `BN_NAME`
   (fixed names, plus per-item and per-text names with valid keys).
2. **Assignment.** Values are unescaped and set with `printf -v`.
3. **Value check.** `valid_design` checks everything the renderer uses in `eval`, `printf`
   formats or `case`:
   - item keys, in `BN_ITEMS`,
   - numbers,
   - choices (layout, icons, art source and size, yes/no),
   - colors.

   Free text (titles, labels, static text, separator, bar characters, art) is only ever
   printed, and `write_conf` quotes it.
4. **Failure.** If any step fails, nothing changes.

**Adapting to the target:**
- `BN_TITLE` becomes the target's community-scripts title when `title=auto`.
- `BN_CREDITS` always comes from the target, so it's empty on a non-community-scripts box.
- `BN_MOUNTS` keeps only mount points that exist there.
- `quiet=yes` sets `QUIET_ON_SAVE`.

## Logo and wordmark

The logo (`assets/logo.svg`, `assets/logo-light.svg`), `assets/wordmark.svg` and the terminal
wordmark (`LOGO_LINES` in the script) use **Null Pointer** by Tom Murphy 7
([Divide By Zero fonts](http://fonts.tom7.com/)). Its license allows graphics and design work,
including commercial work, but not reselling or redistributing modified font files.
- **SVGs:** the glyphs were converted to outlines.
- **Terminal wordmark:** hand-fitted to an 8×6 half-block grid per letter.
- **Never commit the font file.** `.gitignore` blocks `*.ttf` and `*.otf`.

Wordmark gradient colors are xterm 62, 98, 134, 164, 163 and 162. Each has at least 3.9:1
contrast against both white and black.

## Submitting to community-scripts

This repository stays the source. community-scripts gets a **generated copy** in its own
format, so you only ever maintain one `bannarr.sh`.

### Their rules

These come from the [DevScripts README](https://github.com/community-scripts/DevScripts),
its [`AGENTS.md`](https://github.com/community-scripts/DevScripts/blob/main/AGENTS.md), the
add-on template `tools/addon/_template.sh`, and the ProxmoxVE pull request template, as of
October 2026.

| Rule | How Bannarr meets it |
| ---- | -------------------- |
| New scripts go to **DevScripts**, not ProxmoxVE. PRs without prior testing are closed | Open the PR against [community-scripts/DevScripts](https://github.com/community-scripts/DevScripts). Maintainers move it to ProxmoxVE after community testing |
| Add-ons live in `tools/addon/` and run **inside the guest** | `tools/addon/bannarr.sh`, which runs on the box it customises |
| Header: `Copyright (c) 2021-2026 community-scripts ORG`, `Author: Name (GitHubUsername)`, their MIT link, `Source:` the project URL | The generator writes it |
| Source `core.func` and `tools.func` from `COMMUNITY_SCRIPTS_CORE_URL`, as the add-on template does | The generator replaces the `devscripts-core` block with those two lines |
| `APP="…"` and `APP_TYPE="addon"` | Already in `bannarr.sh` |
| Messages name the app; no `$APP` / `${APPLICATION}` placeholders | `bannarr.sh` writes "Bannarr"; checked |
| Every `msg_info` is closed by exactly one `msg_ok`; notices use `msg_warn` | Bannarr has no progress messages, only notices, so it uses `msg_warn`; checked |
| No decorative comment banners (`----`, `====`, `####`) | Removed from `bannarr.sh`; checked |
| No core packages as dependencies (`curl`, `sudo`, `wget`, `jq` and `mc` are pre-installed) | Bannarr installs nothing; checked |
| "No functions of your own" | Applies to `ct/` and `install/` scripts only; add-ons, including the template, define functions |
| AI use must be disclosed, with the model name and reasoning level, and the script must follow their `AGENTS.md` and `pve-script-creator.agent.md` | Pre-filled in the generated PR description; fill in the reasoning level |
| "Tested on:" must be filled in | Test on real containers first (see below) |

### Generate the add-on

```bash
scripts/build-devscripts.sh          # writes dist/devscripts/ (git-ignored)
```

The script writes two files:
- **`dist/devscripts/tools/addon/bannarr.sh`:** the add-on, laid out like their repository.
- **`dist/devscripts/PR_DESCRIPTION.md`:** their PR template, pre-filled. It describes what
  Bannarr does and lists the rules that can't be followed as written, with the reason for each.

It changes 15 lines (header, helper source lines, docs link) and then checks the result
against the rules above. It exits non-zero if any check fails. Never edit the output: change
`bannarr.sh` and run it again.

Two things in `bannarr.sh` exist for the generated copy and must stay:
- **The `devscripts-core` marker block** near the top, where the source lines go.
- **`trap 'exit 130' INT TERM`.** Their `core.func` traps INT and TERM with a handler that only
  stops its spinner, so without this line Ctrl+C would no longer quit the editor.

Their `core.func` and `tools.func` share only three function names with Bannarr: `msg_ok`,
`msg_warn` and `msg_error`. Bannarr defines its own after the source lines, so its versions
win.

### Before opening the pull request

- [ ] Test the **generated** add-on on real containers: Debian, Ubuntu and Alpine at least, plus
      Fedora/Rocky, Arch and openSUSE if possible. Cover a fresh community-scripts container
      (first-run questions, save, SSH login, `--revert`) and a plain VM.
- [ ] Check what `core.func` does when sourced on a real container. It was only compared by
      name here, not run.
- [ ] Run `scripts/build-devscripts.sh`, and make sure every check passes.
- [ ] Fork [community-scripts/DevScripts](https://github.com/community-scripts/DevScripts) and

- [ ] Open the PR with `dist/devscripts/PR_DESCRIPTION.md` as its body. Fill in every `TODO`
